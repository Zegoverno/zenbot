# Plan: zenbot core + the first three plugins

From ADRs 0001–0003. Each step is one or more small PRs, and zenbot keeps working after each.

## 0. Fresh public repos
Each public repo (zenbot, sudoku, reader, writer) starts from a single first commit of a reviewed
tree; earlier history stays private. Commits use the GitHub no-reply address. Before the first
push, and in CI from then on: `gitleaks`, and a read of every file that isn't code. Sudoku ships
with one classic puzzle generated by our own solver and checked to have a unique solution.

## 1. The web app moves into zenbot ✓
- Copy the web app into `web/` as it is (Sudoku left out: it becomes a plugin). `upgrade.sh` builds and installs it, and
  `scripts/check.sh` and CI run its checks and e2e tests.
- Serve the owner's web address from zenbot's build; the old web app repo is retired.
- Web chat slash commands come from `commands.rs`, which the kernel serves, so the web keeps no
  copy of its own.

## 2. Drop the TUI ✓ (but Games, see below)
The web covers what the TUI did; each item's e2e test (`web/tests/zen-e2e.mjs`, by its
comment):
- [x] Board: Sessions (channels, waiting first, subagents, archived, jobs behind `J`, `+ new session`):
  "Channels apart; waiting first", "a `+ new session` button", "Archived jobs stay out"
- [x] Session chat: streaming, folded tool runs, questions with options, suggestions, steer, queue,
  interrupt: "Tool runs fold", "Questions with options", "During a turn"
- [x] Side panel with the same views beside a chat: the side panel checks in the chat part
- [x] Files: tree, new file and folder, rename, and the safety rules (now `web/server/home.ts`):
  "Files:", "couldn't create .env"
- [x] File viewer: reading aids (width, spacing, bionic, focus, play), links, headings,
  next/previous, front matter, changelog: "Reading aids", "Headings", "changelog apart"
- [x] Tasks: open vault tasks by project, hand one to an agent: "Handing a task to an agent"
- [x] Agents: list, edit SOUL/IDENTITY/agent.toml, new, delete, start a session: the Agents checks
- [x] Games: installed plugins contribute games to the Games picker (zensudoku first).
- [x] `zen` CLI script commands unchanged (`cli.rs` test against the shared table)

Removed: `crates/zen/src/tui`, `editor.rs`, `md.rs`, `tex.rs`, `screen.rs`, `zen chat`, `--inline`,
`-c`/`-r`; plain `zen` prints help. The web chat's slash commands come from `zen --commands`.

## 3. Plugin host (core) ✓
- `plugin.json` parser and checks; `zen plugins add | rm | list`; a permission prompt for the owner.
- Plugin MCP servers supervised by `zend` in the sandbox, with their tools on the tape.
- The web shell's MCP Apps host: sandboxed iframe, postMessage bridge, `zen/context`, `zen/open`.
- The `views`, `openers` and `commands` slots. Settings page: installed plugins, the default per slot.
- Built-in defaults: plain Markdown reader and editor, plain Tasks and Agents lists.
- A test plugin in `tests/fixtures/` covers the slots end to end.

## 4. zensudoku (public repo, MIT) ✓
- Fresh repo with the layout of ADR 0003. Move the TS game and its tests out of
  `web/`.
- PWA shell, hosted. MCP server with tools (`sudoku_new`, `sudoku_state`, `sudoku_check`,
  `sudoku_hint`) and the `ui://sudoku/app` view.
- Games remains a shell-owned picker; the game itself is a plugin.

## 5. zenread (public repo, MIT) ✓
- The file viewer's reading side becomes an opener, `*.md` first. PDF, EPUB and saved web pages
  come later, toward a full read-later app.

## 6. zenwrite (public repo, MIT) ✓
- The web app's writer becomes an opener for `*.md` in edit mode, along with its server parts
  (versions, check, shrink, find notes, changelog).
- Its AI goes through the chat when inside zenbot, and through ACP in the Tauri desktop shell.
  zenbot then needs an ACP agent endpoint.

## 7. Store builds
- Mobile shell (Capacitor or Tauri, decided by building Sudoku on iOS). The App Store needs the
  owner's Apple developer account ($99/yr): ask first.

## Asks before acting

- Anything that spends money: hosting beyond free tiers, store accounts.

## Current release limits
Plugin AI sampling is disabled until provider-native output caps and per-plugin budgets exist.
Desktop ACP and store shells remain future work; the standalone PWAs and MCP Apps ship now.
Curated listings and releases are described in [PLUGINS.md](../PLUGINS.md).

# Next: a harness that learns (agreed 2026-11-17)

Phases 4 (work OS: task board, channels, flows) and 5 (ACP, desktop and store shells) wait.

## Phase 0: fixes
- Plugin AI on: a plugin with the `ai` permission may sample, with no token cap. The assist
  model by default, every call recorded, a count and an on/off switch per plugin in Settings.
- The skills index lists each skill with its trigger, not a count per domain.
- The sleep keeps short-term memory under its budget (it is at about 5x today).
- The writing skills ship with zenwrite; the stale zensudoku listing; ADRs 0002 and 0003 accepted.

## Phase 1: roles
- A role is a profile, not an agent: a kind of work, a model, tools and skills
  (`[roles.<name>]` in `agent.toml`). `delegate` takes `role`; when a task has neither role nor
  model, System One picks the role from the task.
- Each agent has a default subagent model (zenbot: Sonnet).

## Phase 2: the learning loop
A session is one job, done end to end: fixes, reviews and corrections happen inside it. The owner
ends it when the work shipped, or when it derailed and a fresh start is better.
- `/archive done | partial | not-done [note]` replaces `/done`; `partial` writes a handoff brief
  for the next session. The `work` tool and the empty `session_scores` table go.
- On archive, a review job rereads the session from the tape and records how the work went: the
  kind of work, the role, model and skills used, the outcome, and how much the owner had to
  intervene (corrections, steers, interrupts, repeated requests, errors), with message numbers.
- From the reviews it decides only two things:
  - a better (or cheaper) model for that kind of work: the role's model;
  - notes for IDENTITY, USER, memory or a skill (applied and reported in the zen room, revertible).
    AGENTS.md and SOUL.md are the owner's: changes there are suggested, never made.
  Model changes need the same pattern in two or more reviews; a single session can add a note.

## Phase 3: one brain for every harness
- `zen mcp`: the kernel's memory, wiki, records and session search as a local MCP server (owner
  token, read or read-write scope, every call recorded), so Claude Code, Claude Desktop and Codex
  share zenbot's second brain.
- A vault-structure plugin packages the owner's method: Daily, Goals, Projects, Skills, Templates
  and the wiki (folders, templates, frontmatter types, wiki rules, lint, a UI). Not PARA.
- Search splits long documents into chunks before embedding.
